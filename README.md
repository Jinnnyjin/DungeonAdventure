## 🎮 게임 소개

절차적으로 생성되는 던전을 탐험하며 몬스터를 처치하고 드랍된 아이템을 파밍해 장비하며 성장하는 액션 로그라이크

**전투 루프**
```
던전 입장 → 방 탐험
  → 몬스터 마주침 → 처치
  → 아이템 드랍 → 습득 → 장착
  → 다음 방 이동
  → 보스 처치 = 승리
   체력 0 = 패배
```

## 🛠 핵심 구현 기술

### 1. 절차적 던전 생성
- 그리드 랜덤워크 방식으로 방을 배치하고 연결 (MVP)
- Room / DungeonGraph는 생성 알고리즘과 무관하게 동작하도록 설계
  → 추후 랜덤워크를 BSP나 MST로 바꿔도, 이 결과물을 쓰는 다른 시스템들은 수정할 필요가 없음
- `DungeonGraph`의 내부 `Dictionary<int, Room>`은 private으로 캡슐화, `GetRoom` / `AddRoom` / `AllRooms` 읽기 전용으로 공개

### 2. 경로탐색 — Dijkstra Map
- 몬스터마다 개별 A*를 도는 대신, **플레이어 위치 기준 거리장을 한 번만 계산**하고 모든 몬스터가 이를 공유 참조
- 몬스터 수가 늘어나도 연산량이 크게 증가하지 않음 (개별 탐색 대비 확장성)
- 거리장 재계산은 매 프레임이 아니라 플레이어가 일정 거리 이상 이동했을 때만 수행
- 던전 레벨(방 단위) / 방 내부(타일 단위) 두 스케일에서 동일 알고리즘을 목적만 다르게 재사용

### 3. 오브젝트 풀링
- 몬스터, 드랍 아이템, 투사체, 이펙트에 `UnityEngine.Pool.ObjectPool<T>` 적용
- 몬스터는 던전 생성 시 일괄 스폰이 아니라 **플레이어가 방에 입장하는 시점에 지연 스폰**

### 4. ScriptableObject 기반 데이터 · 이벤트 아키텍처
- **데이터**: `ItemData`, `MonsterData` 등 정적 데이터를 SO로 관리. 아이템은 슬롯 종류와 무관하게 `statModifiers` 리스트로 통일된 구조를 가져, 새 아이템 추가가 코드 작업이 아닌 데이터(SO 애셋) 작업이 되도록 설계
- **이벤트**: 제네릭 `EventChannelSO<T>` 베이스 클래스 + 타입별 서브클래스로 옵저버 패턴 구현. 발행측(인벤토리, 전투 로직)과 구독측(UI, 스탯 시스템)이 서로 직접 참조하지 않아 느슨한 결합 유지
- SO에는 런타임 상태(현재 체력 등)를 저장하지 않고, 정적 데이터·이벤트 채널로만 사용 (공유 애셋 특성상 상태를 넣으면 인스턴스 간 값이 섞이는 버그 위험)

## ⚔️ 시스템 설계 요약

| 시스템 | 설계 | 비고 |
|---|---|---|
| 몬스터 | 근접형 1종 + 원거리형 1종. 공격 로직은 `AttackBehaviorSO`로 전략 패턴 분리 |  |
| 몬스터 스폰/탐지 | 방 입장 시 지연 스폰, 일정 범위 진입 시 대기→추적 상태 전환 | 근접/원거리 별 탐지 범위 차별화 가능 |
| 장비 | 무기 / 방어구 / 악세서리 3슬롯, 전 슬롯 동일 `ItemData` 구조 | 장비 해제 시 최대 체력 감소분만큼 현재 체력 clamp |
| 스탯 | 공격력 / 방어력 / 이동속도 / 체력 4종 | 장착 아이템의 `statModifiers` 합산으로 재계산 |
| UI | 인벤토리 슬롯 미리 생성 후 재사용, HUD는 이벤트 채널 구독으로 갱신 | Instantiate/Destroy 반복 없이 슬롯 내용만 갱신 |

## 🚧 1차 MVP 스코프

- 던전 방 5~8개 (단순 연결 알고리즘)
- 몬스터 2종 : 근거리, 원거리
- 장비 슬롯 3개 / 아이템 10~15개
- 스탯 4종
- 던전 1개 = 1판 (여러 층 진행은 확장 후보)

**확장 후보**: 던전 생성 알고리즘 고도화(BSP/MST), 아이템 강화 시스템, 아이템 등급 체계, 몬스터 종류 추가

## 🧩 기술 스택

`Unity (2D)` `C#` `ScriptableObject` `UnityEngine.Pool`
